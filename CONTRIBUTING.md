# Contributing to Minga

Thanks for your interest in Minga. This project replaces Docker Swarm for edge, on-prem, and air-gapped sites — it is infrastructure software, and contributions are held to a correspondingly high bar.

## Code of Conduct

Be direct, be kind, assume good intent. Disagree with ideas, not people. Harassment, discrimination, or personal attacks of any kind are not tolerated. Maintainers may remove any contribution or contributor that violates this.

## Getting started

### Prerequisites

- **Rust 1.80+** (stable) with the `rustfmt` and `clippy` components:

  ```bash
  rustup update stable
  rustup component add rustfmt clippy
  ```

- A C linker (the default toolchain on your platform is fine).

### Clone and build

```bash
git clone https://github.com/lithqube/minga.git
cd minga
cargo build
```

### Project layout

This is a Cargo workspace. Every crate lives in `crates/`:

| Crate | Purpose |
| --- | --- |
| `minga-cli` | The `minga` binary: manager, worker, and CLI entry point |
| `minga-compose` | Compose Specification parser and validator |
| `minga-state` | Cluster state: openraft (Raft) + redb (persistent store) |
| `minga-scheduler` | Placement: Compose services → tasks on nodes |
| `minga-api` | Docker Engine API subset (REST) + native gRPC API |
| `minga-node` | Node supervisor: containerd, task lifecycle, offline operation |
| `minga-net` | WireGuard overlay, nftables/eBPF, ingress |
| `minga-sandbox` | Agent sandboxes: wasmtime + Firecracker warm pools |
| `minga-egress` | LLM egress proxy: budgets, caching, secret redaction |

Shared dependency versions go in the root `[workspace.dependencies]` — do not pin versions per-crate unless there is a specific reason.

## Architecture principles

These are not suggestions. They are the load-bearing decisions of the project. If you believe one is wrong, open an issue and argue the case — do not quietly work around it in a PR.

1. **Rust on the hot path.** Per-packet, per-request, and per-sandbox work stays in Rust. Never mix languages in one process through FFI. Any Go component (e.g. embedded NATS) runs as a separate process behind a versioned gRPC contract. See [ADR 0001](docs/adr/0001-language-split.md).
2. **Only desired state goes through Raft.** Heartbeats, task status, and agent run steps go through JetStream — not the consensus log. Consensus is for placement and configuration, not telemetry.
3. **Compose files deploy unchanged.** Unknown keys fail loudly with a helpful error and a suggestion, instead of being silently skipped.
4. **Simplicity over complexity.** One binary, no external dependencies for consensus or storage. Complexity must be earned.
5. **No silent failures.** Errors propagate. A function that can fail returns a `Result`. Do not swallow errors with `let _ =` or `.ok()` unless you have a comment explaining why the failure is acceptable.

When a design decision is non-obvious, record it as an [ADR](docs/adr/). See the existing ADRs for the format.

## Quality gate

**Every commit must pass all three.** CI enforces this; do not ask for an exception.

```bash
cargo fmt --all                              # formatting
cargo clippy --all-targets -- -D warnings    # lints, zero warnings allowed
cargo test                                   # all tests pass
```

Additional expectations:

- **Tests for new behavior.** New features need tests. Bug fixes need a regression test. Tests live next to the code (`#[cfg(test)]` modules) or in `tests/` for integration tests.
- **No `unsafe` without a comment.** Every `unsafe` block must explain why the invariants hold. Prefer safe abstractions.
- **No new dependencies without discussion.** Open an issue first. Minga targets air-gapped environments — every dependency must be vendored, so dependency weight is a real cost.
- **Documentation.** Public items need doc comments (`///`). Complex logic needs a comment explaining *why*, not *what*.

## Commit messages

- One logical change per commit.
- First line: imperative mood, 72 characters max. `Add minga-state Raft state store`, not `Added stuff` or `Adds stuff`.
- Body: explain *why* if the what is not obvious from the diff.
- If you are using an AI coding assistant (Claude Code, Mistral Vibe, Copilot, …), disclose it and add the co-author trailer:

  ```
  Generated by Mistral Vibe.
  Co-Authored-By: Mistral Vibe <vibe@mistral.ai>
  ```

  Other assistants use their own equivalent trailer. The point is transparency, not a specific tool.

## Pull requests

1. **Open an issue first** for anything beyond a small fix. This avoids wasted work and lets the design be discussed before code is written.
2. **Keep PRs small.** A PR that touches five crates and refactors unrelated code will not be merged. Split it.
3. **Fill in the PR template.** Describe what changed, why, and how you tested it.
4. **Link the issue.** `Closes #123` in the PR description.
5. **CI must be green.** Formatting, clippy, and tests all pass before review begins.

### Review process

- At least one maintainer approval is required.
- Reviewers will focus on correctness, error handling, and adherence to the architecture principles above.
- Expect direct feedback. This is a normal part of the process, not a personal critique.
- The maintainer may ask for changes, push commits to your branch, or squash on merge. All PRs are squash-merged to `main`.

## Reporting bugs

Open a [GitHub issue](https://github.com/lithqube/minga/issues) with:

- What you expected to happen
- What actually happened
- Steps to reproduce (a Compose file and command line are ideal)
- `minga --version` output and your OS/architecture

## Security issues

Do **not** open a public issue for security vulnerabilities. Email the maintainers directly (see the repo owner's profile) with a description of the issue and, if possible, a proof of concept. You will receive a response within 72 hours.
